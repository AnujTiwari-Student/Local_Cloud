## CI and CD roadmap

All items in this section are **planned**, unless explicitly described as existing. Configuration belongs in the application's `localcloud.toml`; no GitHub workflow is required. The current parser accepts the documented `[ci]` configuration only. Future stages, deployment settings and commands described here are design goals, not syntax you can use today.

| Area                      | Planned functionality                                                                                                                                                                                           | Completion evidence                                                                                                                                              |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pipeline stages           | Named format, lint, security scan, test, build and deploy steps; explicit dependencies, working directories and environment variables. Use installed tools such as `gofmt`, `go vet`, `go test` and `go build`. | A sample Go application runs each stage, reports its result and skips deployment when a required check fails.                                                    |
| Execution controls        | Stage timeouts, cancellation, conditional execution, bounded retries and optional parallel execution.                                                                                                           | Failure and cancellation tests show that child processes stop and downstream steps follow their configured conditions.                                           |
| Build artifacts           | Save binaries, container image digests, checksums and test/coverage reports per run; configurable retention and dependency caches.                                                                              | Deployment consumes the exact artifact produced by a successful build; previous releases remain identifiable.                                                    |
| Deployment targets        | Start with local Docker/Compose and existing Kubernetes clusters; choose the context, namespace, image and configuration explicitly.                                                                            | A sample application deploys from its own project directory and exposes a working endpoint.                                                                      |
| Environments and releases | Separate development/staging configuration, release history, promotion of an existing artifact and deployment concurrency locks.                                                                                | Two environments keep separate settings; concurrent releases cannot overwrite each other silently.                                                               |
| Health and rollback       | Wait for rollout/readiness, run application smoke checks and restore the previous release on a failed rollout.                                                                                                  | An intentionally unhealthy release fails and the previous working application becomes available again. Database migrations require a separate recovery strategy. |
| Secrets and access        | Secret references, output redaction and permissions for deployment targets; optional manual promotion gates.                                                                                                    | Secret values stay out of reports and saved configuration; unauthorized deployment attempts fail.                                                                |
| Preview environments      | Connect successful builds to existing private Kubernetes previews, attach artifacts and clean up on expiry.                                                                                                     | A test branch gets an isolated endpoint and state, then its preview resources are removed at expiry.                                                             |

The intended workflow is: create the application, put configuration in its directory, run `localcloud ci`, inspect test/build results, then deploy the successful artifact through the future CD runner. Today, `localcloud ci` can run your own deployment script as its application command, but LocalCloud does not manage releases, health checks or rollback for that script.

## Other capability backlog

All items below remain planned beyond the existing subsets in the coverage matrix:

- Multi-account and multi-region state isolation, broader AWS SDK/CLI protocol support and service-specific error compatibility.
- Remote snapshot storage with versions, sharing, access control and retention.
- Provider extensions with versioned hooks, installation and lifecycle management.
- Resource editors, cross-service execution views and dependency graphs in the dashboard.
- Selected-resource replication from an explicitly configured AWS account, with a reviewable import plan.
- Expanded fault scenarios, network disruption and a separately scoped FIS-compatible API.
- MCP integration, team access controls and audit export.

## Implementation order

1. Extract a provider interface and add the AWS operations required by an actual application, with API contract tests.
2. Add account/region namespaces and authenticated management access before remote or shared use.
3. Add a bounded workload runner for Lambda/RDS-style workloads, with lifecycle and resource-limit tests.
4. Extend the implemented private cluster previews with remote snapshot storage, authenticated tenant isolation and optional ingress.
5. Add collaboration, AWS workload API providers, live-resource replication and MCP after the local provider and instance lifecycle contracts are stable.

Prioritize the next increments around a small Go application: named CI checks and build artifacts, Kubernetes CD with health checks and rollback, DynamoDB CRUD, then extend EC2 execution and add EKS lifecycle adapters. Expand each provider only after its initial contract works end to end.

Each additional service should specify operations, request/response shapes, errors, persistence rules and cross-service interactions. A list of 110 service names alone does not define those contracts.
