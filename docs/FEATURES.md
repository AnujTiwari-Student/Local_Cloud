## CI and CD roadmap

All items in this section are **planned**, unless explicitly described as existing. Configuration belongs in the application's `localcloud.toml`; no GitHub workflow is required. The current parser accepts the documented `[ci]` configuration only. Future stages, deployment settings and commands described here are design goals, not syntax you can use today.

| Area                      | Planned functionality                                                                                                                                                                                           | Completion evidence                                                                                                                                              |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pipeline stages           | Named format, lint, security scan, test, build and deploy steps; explicit dependencies, working directories and environment variables. Use installed tools such as `gofmt`, `go vet`, `go test` and `go build`. | A sample Go application runs each stage, reports its result and skips deployment when a required check fails.                                                    |
| Execution controls        | Stage timeouts, cancellation, conditional execution, bounded retries and optional parallel execution.                                                                                                           | Failure and cancellation tests show that child processes stop and downstream steps follow their configured conditions.                                           |
| Build artifacts           | Save binaries, container image digests, checksums and test/coverage reports per run; configurable retention and dependency caches.                                                                              | Deployment consumes the exact artifact produced by a successful build; previous releases remain identifiable.                                                    |
| Deployment targets        | Start with local Docker/Compose and existing Kubernetes clusters; choose the context, namespace, image and configuration explicitly.                                                                            | A sample application deploys from its own project directory and exposes a working endpoint.                                                                      |
| Environments and releases | Separate development/staging configuration, release history, promotion of an existing artifact and deployment concurrency locks.                                                                                | Two environments keep separate settings; concurrent releases cannot overwrite each other silently.                                                               |
| Health and rollback       | Wait for rollout/readiness, run application smoke checks and restore the previous release on a failed rollout.                                                                                                  | An intentionally unhealthy release fails and the previous working application becomes available again. Database migrations require a separate recovery strategy. |
| Secrets and access        | Secret references, output redaction and permissions for deployment targets; optional manual promotion gates.                                                                                                    | Secret values stay out of reports and saved configuration; unauthorized deployment attempts fail.                                                                |
| Preview environments      | Connect successful builds to existing private Kubernetes previews, attach artifacts and clean up on expiry.                                                                                                     | A test branch gets an isolated endpoint and state, then its preview resources are removed at expiry.                                                             |

The intended workflow is: create the application, put configuration in its directory, run `localcloud ci`, inspect test/build results, then deploy the successful artifact through the future CD runner. Today, `localcloud ci` can run your own deployment script as its application command, but LocalCloud does not manage releases, health checks or rollback for that script.

## Other capability backlog

All items below remain planned beyond the existing subsets in the coverage matrix:

- Multi-account and multi-region state isolation, broader AWS SDK/CLI protocol support and service-specific error compatibility.
- Remote snapshot storage with versions, sharing, access control and retention.
- Provider extensions with versioned hooks, installation and lifecycle management.
- Resource editors, cross-service execution views and dependency graphs in the dashboard.
- Selected-resource replication from an explicitly configured AWS account, with a reviewable import plan.
- Expanded fault scenarios, network disruption and a separately scoped FIS-compatible API.
- MCP integration, team access controls and audit export.

## Implementation order

1. Extract a provider interface and add the AWS operations required by an actual application, with API contract tests.
2. Add account/region namespaces and authenticated management access before remote or shared use.
3. Add a bounded workload runner for Lambda/RDS-style workloads, with lifecycle and resource-limit tests.
4. Extend the implemented private cluster previews with remote snapshot storage, authenticated tenant isolation and optional ingress.
5. Add collaboration, AWS workload API providers, live-resource replication and MCP after the local provider and instance lifecycle contracts are stable.

Prioritize the next increments around a small Go application: named CI checks and build artifacts, Kubernetes CD with health checks and rollback, DynamoDB CRUD, then extend EC2 execution and add EKS lifecycle adapters. Expand each provider only after its initial contract works end to end.

Each additional service should specify operations, request/response shapes, errors, persistence rules and cross-service interactions. A list of 110 service names alone does not define those contracts.

## REA MCP validation status

See [the REA service audit](REA_SERVICES.md), [EC2/Kubernetes comparison](REA_EC2_KUBERNETES.md) and [expanded EC2 coverage](EC2_REFERENCE.md). LocalStack 2026.10.0 starts with the supplied token. All nine bounded EC2 lifecycle projections now match. Both backends were exercised with 27 Boto3 scenarios; tags, filters, image discovery, attributes, user data and persistent launch idempotency were added. LocalCloud passed 141 tests and 11 isolated runtime checks, plus separate live Docker user-data/recovery and kind operator/Job checks. The reference's ClientToken reuse and start-after-termination behavior intentionally differ. The later [EC2 infrastructure milestone](EC2_INFRASTRUCTURE.md) adds 70 selected AWS operations, pagination, networks, filesystem volumes/snapshots, IMDS and SSH. Full EC2 response/parameter parity remains unfinished; the later [Kubernetes EC2 adapter](EC2_KUBERNETES.md) implements the bounded workload path. The reference Kubernetes backend created an EC2 Deployment/Pod, but that probe's AMI image failed to pull. Full parity and reference-operator reconciliation remain unverified. Planned services retain their existing status.

### EC2 infrastructure verification, 20 October 2026

The current EC2 subset adds independent implementations informed by normal-license
REA observations: 47 Boto3 infrastructure scenarios per backend (46 matching HTTP
statuses), live Docker web/IMDSv2/file snapshot restore and SSH/root preservation.
These checks do not certify complete EC2 equivalence. See
[the full guide](EC2_INFRASTRUCTURE.md) for resource limits, unsupported behavior
and reproducible usage. CI/CD and EKS retain their separate existing scopes.

### EC2 networking REA follow-up, 20 October 2026

The EC2 subset now has 74 AWS operations plus NameInstance. ENI attributes,
secondary-IP assignment/removal, default groups, IP reservation and EIP
associations are implemented, including dashboard controls. Both mock and Docker
backends support these control-plane records. REA demonstrated that the tested
LocalStack Docker backend did not enforce SG changes or add actual guest NICs,
and its EIP did not forward the tested HTTP port. LocalCloud likewise makes no
claim of AWS packet-level networking. See [the networking evidence and usage](EC2_NETWORKING.md),
including deliberate validation/response differences.

### EC2 release checkpoint — 20 October 2026

97 selected AWS operations plus NameInstance now have registered handlers. The
new checkpoint adds image lifecycle, owned stopped Docker-root AMI capture,
launch templates/versions and template launches, snapshot copies and batches,
volume/snapshot attributes and single-region discovery. 181 tests passed, with
Boto3 replays and an actual Docker AMI clone test. This is a verified local
subset, not full LocalStack EC2 equivalence. See [usage and limits](EC2_RELEASE.md).

EC2 storage follow-up (24 October 2026): emulated EBS encryption-default flags, full volume-modification history, SDK string-based snapshot tag copying and one journaled guest pause across batch copies. See [behavior, differences and evidence](REA_EC2_STORAGE_FOLLOWUP.md). These flags do not provide at-rest encryption or raw block devices.

EC2 Kubernetes recovery follow-up (25 October 2026): durable provisioning/update/delete intents, post-commit UID-bound cleanup, desired-state reconciliation, safe missing-data handling and direct minimal-role live verification. See [audit and operational recovery](REA_EC2_KUBERNETES_COMPLETION.md). CSI storage and IAM credentials remain separate work.

### EC2 Kubernetes bootstrap metadata follow-up

With an EC2 helper image configured, metadata now starts before user-data initialization and stays available to the guest. Native restartable init sidecars and a startup probe gate initialization; both containers receive the Pod-local metadata endpoint. Requires Kubernetes native sidecar support (enabled by default from 1.29). IMDSv2 and existing metadata options apply during initialization. At this bootstrap checkpoint IAM/STS credentials were separate work; the later [instance-role implementation](EC2_INSTANCE_ROLES.md) now adds them. See [bootstrap metadata evidence and usage](REA_EC2_KUBERNETES_BOOTSTRAP.md) and the [runnable setup](EC2_KUBERNETES.md#optional-instance-metadata).

### EC2 instance roles and temporary credentials

IAM roles, inline policies and instance profiles; EC2 launch/association/replacement/disassociation; STS AssumeRole/GetCallerIdentity; IMDSv2 role credential delivery; demand-driven rotation and revocation; and SigV4 validation for locally issued sessions are implemented. `--iam enforce` evaluates the role policies for supported requests. Docker and Kubernetes helpers use an instance-scoped credential broker and require a guest-reachable public backend endpoint. See [setup and application example](EC2_INSTANCE_ROLES.md) and [REA evidence and differences](REA_EC2_INSTANCE_ROLES.md). Managed policies, conditions, federation, broader STS and account/region isolation remain future work.
